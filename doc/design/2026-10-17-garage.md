# The garage door, from the dash

Owner, 2026-10-17: "can I control my myQ garage door opener". This is a design
only. Nothing here is built yet, and it needs one piece of hardware.

## myQ itself: no

Chamberlain blocked third-party access to the myQ API in November 2023, and
has not reversed it. Home Assistant removed its myQ integration in its
2023.12 release and pointed users to other solutions. Homebridge plugins broke
at the same time. Any OmaCar integration that logged in to myQ would mean
holding the owner's myQ password and pretending to be Chamberlain's app,
against their terms and liable to break without warning. So no.

Sources: [TechHive](https://www.techhive.com/article/2130930/chamberlain-myq-garage-door-controller-homebridge-home-assistant-blocked.html),
[Kowatek summary of The Verge](https://blog.kowatek.com/?p=33916).

## The way people do it now: a local controller at the opener

A small Wi-Fi board wired to the opener's wall-button terminals speaks the
opener's own protocol, so it doesn't need the cloud, an account or myQ.

| Board | What it is | Protocols | Local APIs |
|---|---|---|---|
| **ratgdo32** (Paul Wieland) | ESP32 board | Security+ 1.0, Security+ 2.0, dry contact | ESPHome (native API, web server REST and SSE), MQTT, HomeKit |
| **Konnected GDO blaQ** | ESP32-S3, built on gdolib (Konnected's rewrite of ratgdo's protocol work, Nov 2024) | Security+ 1.0, Security+ 2.0, dry contact | ESPHome native API, ESPHome web server REST and SSE, experimental Matter |

Sources: [ratgdo](https://github.com/PaulWieland/ratgdo),
[Konnected on gdolib](https://community.konnected.io/t/how-konnected-re-wrote-ratgdo-to-secure-the-future-of-the-open-garage-door/36571),
[ratgdo32 on Selora](https://selorahomes.com/devices/ratgdo/ratgdo32/).

**The owner's check before buying.** Look at the opener's learn button. Yellow
means Security+ 2.0, and purple, red or orange means 1.0; both are supported.
A myQ hub can stay installed, but it is not needed once the board is in.

**Recommendation:** the Konnected blaQ if the owner wants it boxed, finished
and supported; the ratgdo32 if they want the original open hardware. Either
way, flash or keep **ESPHome firmware**, because OmaCar talks to its web server.

## How the car reaches it

The garage board is on the home Wi-Fi. The car tablet is on Tailscale, so a
machine at home on the same LAN becomes a **Tailscale subnet router for one
address only**:

```
tailscale up --advertise-routes=192.168.x.y/32     # the garage board, nothing else
```

A Tailscale ACL lets only the car tablet (`omacar-1`) reach that /32, and only
on port 80. Nothing on the home network is exposed to the internet, and the
tablet can't see the rest of the LAN.

## What OmaCar talks to

The ESPHome web server, over HTTP inside the tailnet (WireGuard already
encrypts it):

| Call | Purpose |
|---|---|
| `GET /cover/<door>` | state: open, closed, opening, closing, and position |
| `POST /cover/<door>/open`, `/close`, `/stop` | the commands |
| `GET /events` | the SSE stream; the card updates live with no polling |
| `GET /light/<light>`, `/lock/<lock>` | the opener's light and lock-out, if wired |

ESPHome's web server `auth` (username and password) is turned on. The
credentials live on the tablet in `~/.config/omacar/garage.json` (mode 600),
never in the repo or in a URL.

All Python stdlib: `urllib` for the commands and a line reader for SSE, so the
venv doesn't need to grow.

## On the screen

- **Cabin → Garage:**
  - a door drawn to its real position, animated as it moves (the one motion
    that answers what the door is doing);
  - the state in words, with an Open or Close key and Stop while it moves;
  - the light;
  - "Last changed 4 min ago".
- **Home card (optional):** the same door, small, with one key.
- **Source lamp:** "Home network", "Not reachable" (the tablet is offline or
  the router is down), or "Simulated".

## Safety and the rules

- **Open:** one tap, allowed while driving. That's what the button is for:
  approaching home. It is the same act as a visor remote.
- **Close:** **hold for 1 s**. A door closing on something is the one way this
  can hurt someone, and a hold can't happen by accident on a bumpy road.
  UL 325 requires an opener closed remotely, out of sight, to warn with light
  and sound first. Security+ 2.0 openers and these boards do that themselves.
  OmaCar never bypasses it and never offers "close without warning".
- **Never automatic.** No geofence auto-open or auto-close. The car has no GPS
  yet, and an automatic door is a decision the owner should make separately,
  later.
- **Every command is logged** with time and result
  (`~/.local/share/omacar/garage.log`).

## The build, once the board is installed

1. `lib/garage_door.py`: a client, an SSE follower, a state file and a
   simulator. It follows the fridge pattern (`lib/fridge.py`).
2. `/api/garage`: GET for state; POST for open, close or stop. A hold-to-close
   token prevents a single POST from closing.
3. The Cabin → Garage view and tile, plus an optional Home card.
4. `omacar garage setup`: asks for the board's address and credentials, tests
   them, and writes the config.
5. Tests: the protocol against a fake ESPHome server, hold-to-close, and that
   no credential ever appears in logs, state or the API.
